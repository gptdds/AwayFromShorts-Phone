## 1. 新增功能

- 两个 APK 共用 `WeeklyRule`，支持独立应用规则、星期、多时段、跨午夜、工作日、周末和全天配置。
- 增加真实状态切换时间 `nextTransition`。没有切换时返回 0，避免把后台一小时后的检查点显示成解冻倒计时。后台 `nextFlip` 的检查兜底仍保留。
- 修复夏令时回拨时漏掉重复小时的计算问题；按真实时间推进，再读取当地星期和分钟。
- 无障碍版增加逐应用规则页：图标、名称、状态、星期、多段时间、下一切换时间；支持编辑、添加、删除时段。空星期、全天和重叠时段给出语义提示，合法设置不被无故拒绝。
- DO 冻结时段编辑器补充相同的提示。编辑、导入和批量更改保留既有锁定边界。
- 首页倒计时从规则计算；回前台、时区变化、规则修改和跨越边界后重新校准。DO 首页显示系统实际暂停/隐藏数量；学习和额度仍独立参与最终执行，界面把时间表的倒计时标为“计划切换”。无障碍版显示需拦截数和真实连接状态。
- 两版新增独立系统诊断页。显示真实服务连接、近期巡检、权限、排程请求、实际回调、开机注册和执行结果；DO 额外比较规则与系统暂停/隐藏状态。修复入口只提供重新应用当前规则和对应系统设置。
- 两版增加 JSON 规则备份、版本检查、导入预览、合并/替换策略、恢复前备份和失败回滚。继续保留原有整合 ZIP 数据备份。

## 3. 数据迁移与恢复边界

| 版本 | 迁移方式 | 保护措施 |
| --- | --- | --- |
| DO 旧全局配置 | `targets + days + start_min + end_min` 转为每应用的 `rules` JSON | 保留旧键，保存迁移快照；已有 `rules` 时不再迁移；单次同步写入 |
| DO 已有逐应用 JSON | 沿用原格式，由现有 `Rule` 适配共享核心 | 不批量重写已有规则；`g`、`freeze` 和加入时间沿用原含义 |
| 无障碍旧全局配置 | 展开到 `app_rules_v1`，每个原已选应用获得相同的放行规则 | 保留 `force_until`、`configured`、旧时间与名单；已有新规则时只校验，不覆盖 |

跨午夜凌晨按时段起始日的星期位判定；起止相同表示选中星期全天；空星期/空时段的意义由模式决定。

JSON 备份只包含规则、必要的默认时段、关键应用和无障碍强制结束时间。设备管理身份、系统权限、Shizuku 授权、云端密钥和认证信息不进入此格式。两类 APK 的备份有明确类型，不能误导入另一类执行器。

恢复前保存到应用私有目录 `files/rule-backups/before-时间戳.json`。格式、版本和规则错误均在写入前拒绝；预览后使用已校验的数据，避免重新读取外部文件时内容变化。写入前再次检查锁定；写入失败恢复原配置。DO 恢复保留本机已有应用的加入时间，不重新授予宽限。无障碍强制结束时间取原值和导入值的较大者。

**DO 规则覆盖恢复沿用 `LocalBackup.mayRestore()`：设备管理已启用且首次配置期已结束时拒绝恢复。** 本轮未放宽此边界。无障碍版在强制模式或任一现有规则锁定时拒绝编辑与导入。

### 可靠性改动

- `javac` 失败明确终止，不继续打包；受控非法源码验证失败路径。
- 保留现有常驻服务和 Partial WakeLock；销毁时释放锁并取消四类 Handler 回调，包括此前遗漏的局域网回调。
- 销毁后不再接续旧的异步回调；重复启动前先移除同类任务。
- 系统冻结/隐藏状态未变化时不重复提交暂停操作；执行后读取系统结果，拒绝或状态不符时记录失败。
- 无障碍延迟杀进程前重新检查应用规则，避免跨过放行边界后继续杀应用；后台巡检避免重叠。
- 自愈恢复无障碍名单时保留其他已启用的服务，不再直接覆盖名单。
- 已做模拟器重启恢复检查；服务、排程和回调证据随设备日志保存。
- 重启后系统先报告启动完成，随后才投递开机广播；早期采样保留在 `reboot-early-result.json`，最终以收到广播并实际出现两个服务为通过依据，结果见 `reboot-result.json`。

## 5. 未解决的问题与后续计划

- PLR110 真机已完成安装、规则一致性、诊断、备份和锁定恢复验收；长期灭屏/Doze、低电量、厂商后台清理及 24 小时连续运行仍未做真机长测。API 34 模拟器结果不代表这些环境已通过。
- 无障碍版（含 Shizuku force-stop）只在 API 34 模拟器验证，未在 PLR110 真机覆盖；本轮真机验收针对 DO 守卫版。
- 既有 Shizuku 客户端使用 `newProcess`，依赖 README 指定的 12.x。本机缓存的 13.x 不作为兼容性通过结果；跨大版本适配另行处理。
- 仓库仍追踪开发签名库，原无障碍构建仍有开发签名口令。已识别风险，没有删除、轮换或替换发布密钥。下一阶段可在保持升级签名连续性的前提下改为本地注入。
- 模拟器强化停止验证中遇到一次系统服务重启，以及覆盖安装后无障碍连接尚未建立的失败。测试脚本已改为安装前确认所有者，并在独立模拟器明确重连服务；最终结果来自重跑后的成功记录。

后续验证顺序：先在手机核对现有规则和配置备份，再用最小测试应用验证时段切换、额度/学习叠加、重启恢复与屏幕关闭后的边界；记录最大延迟、电池消耗和失败原因，再决定是否调整 WakeLock 或节拍。不要未经兼容性测试移除现有守护机制。

对照本次工作区的 `AwayFromShorts/src/quota-rules.ps1`、`src/game-quota.ps1`、`src/web/index.html` 及 README 中的独立／共享限额功能实现。未修改电脑版。

## 手机入口与规则

冻结应用 → 每日限额 · 独立 / 共享 → 管理每日限额。

- 可选择本机应用，一应用一格独立计时，或多个应用放一格共用额度。新增默认120分钟，可设1–1440整数分钟。相同应用不能重复放入多个格子。
- 支持修改、合并、拆分、移除、启停。合并默认取所选格子的最小上限，可在保存前调整；拆分后各应用沿用共享格子的上限，分别扣除各自实际已用时间。
- **挂起被拒时的兜底（1.90.6）**：部分 ROM 不允许挂起系统应用。真机实测（OPPO）：额度超额时 Chrome `suspended=true`，Google Play 商店 `suspended=false`，也就是**根本冻不上**，用户只能看到「锁不住」。现在 `setPackagesSuspended` 返回失败名单时自动改用 `setApplicationHidden`：图标消失、点不开，放行时恢复显示，结果页写「已冻结（隐藏）」。两条路都被拒时才写「冻结被系统拒绝」。
- **隐藏应用不能被当成已卸载（1.90.6）**：`setApplicationHidden` 之后，普通 `getPackageInfo(pkg, 0)` 查不到，和已卸载表现一致 —— 额度清理会把它从格子里删掉（实测 Play 商店被删）。判定统一走 `MATCH_UNINSTALLED_PACKAGES` + `ApplicationInfo.FLAG_INSTALLED`；应用名（`labelOf`）也要带这个 flag 才能取到。
- **查询分块（1.90.3）**：`spans()` 按 1 小时一块查询使用记录再拼接解析。单次 `queryEvents` 跨度过大时结果会被截断，且丢的是**最新**事件；额度日从 08:00 起算，凌晨这段窗口长达 22 小时，重度使用的日子照样会截断（表现为额度不涨、限额不触发）。分块后每块都很小，绕开上限。
- **冻结结果要检查返回值（1.90.3）**：`setPackagesSuspended` 不抛异常 ≠ 成功，被拒绝的包名在返回数组里。判定为拒绝时界面写「冻结被系统拒绝」，不再显示成「已冻结」，也不再计入冻结计数。
- **统计口径（1.89.2 修正）**：账本不再按窗口增量累加，而是每次刷新用「今天这段」的前台区间**重算**（只升不降）。增量法只要有一次刷新没拿到用量（事件延迟、进程被重启、权限抖动），那一小段就永久丢失——真机实测一天能丢九成（Telegram 真实 87 分钟只记了 1.9 分钟）。另一个隐藏坑：读使用记录时查了 7 天窗口，事件量一大系统会截断并丢掉**最新**的事件，表现为「正在用，账本不动」；现在只查额度日起点前 6 小时。
- 账本里的 `since` 是这份账本开始统计的时刻（当天账本新建 / 启用额度那一刻），早于它的用量不计；老账本没有这个字段时按额度日起点自愈重算。
- 用量按包名保存，不绑定可变格子，合并拆分和移除再加不会清空。只计启用并纳入限额后的前台时间，停用和移除期间不计；后台、锁屏、灭屏不计。补查系统事件可恢复进程停留期间的有效前台用量，本机零点重置。
- **挂后台也计时（1.87.0 引入，1.88.0 修正口径）**：格子里可以给任意成员勾选「挂后台也计时」。勾中的应用切到后台后，只要**还在跑**（音乐播放、画中画这类前台服务在运行，即系统使用记录里的 FOREGROUND_SERVICE_START → STOP 区间）就继续计时，锁屏、灭屏不打断；应用被关掉（服务停止）就停，切走闲置、纯缓存存活都不计。挂后台区间与前台区间取**并集**（重叠合并成一段，不双倍计）；应用自身绑定的冻结时段照旧豁免。不勾的应用维持只计前台。新增勾选随时可以；取消勾选和移出应用一样只能在调整时段做。
- 应用、上限、分组、限额开关原先仅每天21:00–21:59可改；2026-10-30 起用户要求放开，`DailyQuotaData.EDIT_WINDOW=false` 表示随时可改，页面显示「随时可修改 · 当天已用时间保留」，控件不再禁用，Store 也不再拦截写入。把常量改回 true 就恢复旧的 21:00–21:59 窗口：判定、提示和 `nextEdit` 都还留着，不需要重写。
- 使用情况权限先放开：未授权时额度照常保存，但不计时、不冻结，授权后立即恢复计时与冻结。已授权但事件不可读、用量损坏或无法保存时保护性冻结，损坏用量的保护持续至次日。额度耗尽约每5秒检查并通过设备所有者的暂停应用能力冻结；若那只应用正好停在前台，同一节拍会主动把“今天的额度用完了”提示页拉到最前，当场结束这次使用，不必等用户退出。
- 新全天限额独立于原有 `AppUsageQuota`。原有“放进时段只计该时段、额度用尽才冻结”及旧全天额度保持原样。新限额不会改变时段规则；暂停或移除新限额也不会解除原有时段、学习联动或禁忌冻结。只有关键应用豁免学习闸门，关键应用也不能豁免每日限额，热爱奖励不能抵扣每日限额。

## 实现边界

- `DailyQuotaData`：纯数据模型，配置校验、多应用唯一分组、包级用量、水位、零点切分、固定修改窗口。
- `DailyQuotaStore`：`afs_daily_quota/config`与`usage`，在同一SharedPreferences提交中原子保存配置和当前账本。每次修改先用旧配置结算至当前时刻，再换配置，避免新应用追溯旧时间或停用期间计时。
- `DailyQuotaActivity`：跟随主题的原生设置、应用选择、独立／共享格子和剩余额度。
- `Guard`：合并时段和新限额的目标集合；原因5为每日限额耗尽，任何其他冻结仍保留。新限额应用默认参与学习闸门；关键名单可包括这些应用。
- `GuardService`：后台独立工作线程约5秒检查新限额，达到／恢复额度边界时触发统一Guard.apply；原有30秒守卫节拍保持。
- `FreezeBoardActivity`：新增独立入口、支持拖入应用，显示新限额及真实冻结原因；返回设置后刷新配置并保留页面位置。
- `LocalBackup`：本机完整备份包含新配置和用量，不包含凭据。恢复仍受原有设备管理／宽限期限制。

### 1.58.12 方案 A：额度改成“一行一个格子”，旧全天额度并进来

- 冻结页「使用限额」区不再按应用列额度，而是**一行一个额度（格子）**：图标 + 名称 + 「已用 x / y 分钟 · 剩余 z 分钟」+ 条。点一行 → 新建/修改额度对话框（名称、每天分钟数、勾选成员）；长按 → 菜单（修改 / 并到另一个额度 / 删除）。勾一个成员就是单独额度，勾多个就是共用一份，不需要再“合并”。
- 旧「全天限时」（`AppUsageQuota`，一只应用一份、天生不能共享）在进程启动时并进每日限额：`DailyQuotaStore.migrateLegacy` 把每只应用转成一个单成员格子（分钟数照搬，今天已用时间用 `AppUsageQuota.used` 结算后写进账本），然后清空旧表并置 `enabled=true`。只在有使用情况权限时迁移（否则今天的用量会归零），迁移前把旧的 `config/usage` 与 `limits` 分别留在 `afs_daily_quota/config_before_migration`、`usage_before_migration`、`afs_usage_quota/limits_before_migration`，便于回滚。
- 数据模型不变：一个格子＝`{id,name,minutes,apps[]}`，用量仍按包名列。所以合并只是把成员挪进目标格子（`DailyQuotaData.mergeInto`，分钟取两者较小值），今天已用自动累加；删除（`DailyQuotaData.without`）不动账本。
- 时段卡片里同样用这张额度卡：只列“在这个时段里有成员”的格子，没有额度的应用不再单独列行。
- 管理限额页保留独立入口（启用开关、使用情况权限、添加/编辑/删除），但没有任何合并/拆分按钮。

### 1.90.x 修复：卸载清格子 + 共享格子优先于冻结时段（2026-11-04）

用户反馈三件事，一起收在这一版：

1. **卸载的应用自动退出限额格子**（「MusicFree 都卸载了，怎么还在限额格子里」）。额度只按包名存，卸载既不触发移除，也不会让它退出共享合计——格子里会一直挂着一只已卸载的应用、还占着当天那份用量。新增 `DailyQuotaData.pruneUninstalled(config, usage, installed)`（纯数据、离线可测）：从每格成员和「挂后台」名单里摘掉未安装的包，整格都是已卸载就删掉那格，账本里这些包的 `targets` 已用时间一并抹掉（共享合计随之变小）；若清空后格子全没了且原来 `enabled`，顺手把 `enabled` 置 `false` 保证配置仍合法。由 `DailyQuotaStore.pruneUninstalled(Context)` 在每次 `Guard.apply` 开头运行（`getPackageInfo` 判在装，无变化不写盘），处理后 `refreshed=0` 让快照重建，冻结页下一拍即反映。
2. **共享格子优先于自身冻结时段**。「同一应用既在冻结时段又在共享格子」时按共享格子判：额度没满就放行，满了就冻，冻结时段不再单独压制它。原来 `DailyQuotaStore.exceeded` 里本机这一份被 `inScope`（在自己放行时段内就跳过）挡住，于是「共享额度已用尽、但应用正好在自己的放行时段」时不冻结。现在把优先级抽成纯函数 `DailyQuotaData.exceededBy(shared, localExceeded, inScope, lanExhausted)`：共享组一律 `localExceeded || lanExhausted`（不受 `inScope` 约束），独立组仍沿用 `inScope && localExceeded` 的旧口径。
3. **共享额度用尽时按「额度用尽」冻结**（`nextplayer` 的案例）——即第 2 条的必然结果：共享合计满了，无论是否在自身放行时段，都以原因 5／4 冻结。

离线回归：`DailyQuotaTest` 由 35 项扩到 **96 项**（新增共享优先 5 项、卸载清理 8 项），`GuardTest` 207 PASS / 0 FAIL，全套 `dpc/test/run.sh` EXIT=0。

### 1.91.86 追加：互斥格 5 分钟到点后的强制退出（2026-11-15）
